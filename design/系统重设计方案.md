# 口腔诊所管理系统 · 重设计方案

> 本文只做设计与决策，不含代码改动。确认后按文末分阶段实施。

---

## 一、先定生意：这系统替诊所赚什么钱

单店口腔诊所（1–3 椅位、2–5 名医生）的经营结构：

- **产能刚性**：一天产能 = 椅位数 × 出诊小时数，卖不掉的椅位直接变成本。
- **收入三段**：初诊转化（检查 → 治疗计划 → 成交）、复购（洁牙/复查召回）、高值项目（冠桥、种植、正畸，分次付费）。
- **成本刚性**：房租与人力固定，耗材变动，所以**空椅与爽约是最大利润杀手**。
- **客户生命周期**：初诊 → 计划 → 分次执行 → 维护期 → 召回。

由此，系统要服务的三个目标，按优先级：

| 优先级 | 经营目标 | 系统要支撑的东西 |
|---|---|---|
| 1 | 提高椅位产出 | 排班号源、预约、爽约治理、确认周期 |
| 2 | 提高单客价值 | **治疗计划**、分次执行、成交率、召回回诊 |
| 3 | 守住现金流 | 应收、分次付款、欠款、退款 |

**当前系统的致命缺口在第 2 项**：没有治疗计划，系统就只能记流水，不能管经营。

## 二、诊断：现在的耦合到底卡在哪

不是"患者不该看订单"这种表层问题。根因是三条耦合：

### 根因 1：单据没有正确的父对象
现在 `bill` 与 `dental_order` 都挂在 `encounter` 上。但 `encounter` 只是"一次到诊的一句话病历"，它承载不了：

- 一颗牙的根管治疗分 3 次完成（3 次到诊，1 个治疗目标）
- 一次到诊同时做 2 颗牙（1 次到诊，2 个治疗目标）
- 分次付款（1 个治疗目标，2 张收费单）

所以"再次就诊"和"这颗牙做完没有"这两个问题，现有模型答不出来。

### 根因 2：内部单据被当成对外语言
订单号、技工所、八态状态机、返工原因是**生产过程**；患者要的是**结果**（做到哪一步、什么时候来）。两者不投影，就必然出现"患者管理义齿订单"这种别扭结构。

### 根因 3：内部界面按"数据表"组织，不按"工作队列"组织
前台每天要回答的是"今天谁来、谁没确认、谁该回访"，现在打开工作台看到的是统计卡片。

三条耦合叠加的结果：每改一个地方都要动别处。只修 1 会破报表口径，只修 2 会让患者看不到进度，只修 3 没有数据支撑。

## 三、边界规则（可复用判据）

内部作业面与患者面不是"模块减一半"，而是两套语言。判定规则：

1. 一个概念若**患者不参与其产生**，不得出现在患者面（订单、技工所、诊室、状态机、折扣审批、账龄）。
2. 一个概念若**结果对患者有意义**，必须以患者语言投影后出现（诊断 → 治疗进度；订单 → 制作状态）。
3. 一个概念若**必须由患者本人决定**，必须出现在患者面（选哪个时段、付不付款、是否继续治疗）。

用这三条回扫现有功能：

| 功能 | 患者参与产生 | 结果有意义 | 患者本人决定 | 结论 |
|---|---|---|---|---|
| 预约 | ✔ | ✔ | ✔ | 保留（号源选号） |
| 收费 | ✔（付款） | ✔ | ✔ | 保留，只给应收/已付/待付 |
| 诊疗记录 | ✘ | ✔ | ✘ | 投影为"治疗进度" |
| 义齿订单 | ✘ | ✔（仅进度） | ✘ | 投影为三态，不给单据 |
| 排班/召回/统计 | ✘ | ✘ | ✘ | 不出边界 |
| 折扣原因/账龄/绩效 | ✘ | ✘ | ✘ | 不出边界 |

## 四、领域模型重构（核心）

### 4.1 目标聚合

```
患者 1 ──< 治疗计划 1 ──< 计划项（牙位 + 项目 + 期次）
                              │
                              ├──> 收费单（可分次）
                              ├──> 技工单（修复类项目）
                              └──> 就诊执行记录
预约 ──> 就诊执行记录（资源占用与执行时点）
```

要点：

- **计划项是执行、收费、技工三者的唯一锚点**。
- `encounter` 语义收紧为"一次到诊的执行记录"，不再是单据的父对象。
- `bill.plan_item_id`、`dental_order.plan_item_id` 必填（历史数据回填默认计划项）。
- 保留 `bill.encounter_id` / `order.encounter_id` 作为执行上下文，可空。

### 4.2 新增表（23 → 25）

**treatment_plan 治疗计划**

| 字段 | 说明 |
|---|---|
| id / plan_no | 主键 / 业务编号 |
| patient_id | FK patient |
| doctor_id | FK employee |
| chief_complaint / diagnosis | 主诉与诊断 |
| stage | 拟定 / 已确认 / 执行中 / 已完成 / 已终止 |
| quoted_amount | 报价合计（生成时快照） |
| accepted_at / closed_at | 患者确认时间 / 关闭时间 |
| created_by / created_at | 审计字段 |

**plan_item 计划项**

| 字段 | 说明 |
|---|---|
| id | 主键 |
| plan_id | FK treatment_plan |
| tooth_code | 牙位（FDI，可空表示全口项目） |
| price_item_id | FK price_item（同价位目） |
| phase_no | 期次（1、2、3…） |
| name / quantity / unit_price | 项目快照 |
| stage | 待执行 / 已执行 / 已取消 |
| encounter_id | 执行时所属就诊（可空） |
| bill_id / lab_order_id | 产生的收费单 / 技工单（可空） |
| planned_at / executed_at | 计划时点 / 执行时点 |

### 4.3 修改既有表

| 表 | 变更 | 理由 |
|---|---|---|
| bill | + plan_item_id | 收费必须能追溯到治疗目标 |
| dental_order | + plan_item_id | 一颗牙的冠对应一个计划项 |
| encounter | 语义收紧 + plan_id（可空） | 到诊归属计划 |
| （其余） | 不变 | 状态机、金额口径、召回、排班均保留 |

### 4.4 数据迁移

历史数据不重写：为每条既有 `encounter` 生成一份"单期计划"，把它的收费单与技工单挂到对应计划项。这样新旧并存，报表口径不变。

## 五、系统功能结构（目标态）

### 5.1 内部面：按岗位的一天组织

| 角色 | 首页应是 | 核心动作 |
|---|---|---|
| 前台 | 今日队列（待确认 / 待到诊 / 待回访 / 欠费） | 建约、改约、签到、回访 |
| 医生 | 我的今日患者 | 接诊、病历、牙位图、开计划、执行、开单 |
| 收费 | 待收与欠款 | 收费、分次付款、退款 |
| 负责人 | 经营看板 | 产能、转化、应收、召回效果 |

### 5.2 患者面：三个动词

- **约**：号源自助预约（已实现）
- **看**：治疗计划进度（"还要来 2 次""这颗牙做到第 2 步"）
- **付**：应收 / 已付 / 待付

修复件在患者侧只有三态：制作中 / 待试戴 / 可取件。

## 六、质量属性（必须可验证）

| 属性 | 要求 | 验证 |
|---|---|---|
| 一致性 | 号源不超卖；计划项不重复执行；订单状态不回退 | 并发测试 |
| 可追溯 | 计划变更、执行、收费、退款留痕（人/时/原值/新值/原因） | 抽样回放 |
| 安全 | 患者仅见本人；员工按角色 | 权限矩阵 |
| 性能 | 号源 < 2s；统计 < 5s | 压测 |
| 可恢复 | 每日备份 + 恢复演练 | 备份记录 |

## 七、自我批判（这些判断可能错在哪）

1. **加计划会不会过度设计？** 对课程作业确实重（+2 表、重画 ERD）。但它解决的是"单据无父对象"的结构问题，不加则永远只能记流水。若放弃，需接受"经营目标 2 无支撑"。
2. **bill 改挂计划项会不会破坏统计？** 欠款回收率按 bill 计算不受影响；"记录关联完整度"判定路径变长，需重写口径说明。
3. **患者"我的费用"是否该并入"我的治疗"？** 保留独立入口，因为"我要付钱"是独立意图。
4. **牙位图做多重？** 做 32 格简化版（状态着色），不做解剖图，控制工作量。
5. **旧数据回填默认计划** 会让历史计划的"期次"失真，但保证不破坏既有记录，可接受。
